## 現在地
デスクトップを表示する PC 本体・キーボード・マウス・夜の机を、three.js（r186、jsDelivr から import map と SRI で読み込む）のポリゴンで描いている。シーンは `js/pc3d-scene.js`、カメラ・DOM スクリーン・操作・起動演出は `js/pc3d.js`。
本物の DOM スクリーンは CSS の `matrix3d` でブラウン管のガラスに貼り、着席時は整数 `translate` に戻すので既存アプリの操作はそのまま動く。
描画は常に全解像度で、カメラや画面の色が変わったときだけ行う。ヘッドレス Chrome・M1 Pro・DPR2 の往復テストで全フレーム16.7ms（2026年10月3日時点）。オフラインや WebGL2 なしでは平面モニターに戻る。
three.js 版は main にマージして origin へ push 済み（2026年10月3日時点）。ユーザーの実機で「良い感じに動いている」と確認をもらった。

### 2026-10-03
#### Tab でタスクバーへ移ると画面の黒枠がずれる不具合を修正
- 要望: PC の中を操作中に Tab で画面下のタスクバーへ移ると、画面が下へずれ、ディスプレイの黒枠がずれる。
- 原因: `#screen` は440×330・枠3px の border-box で、中身が縦に6px はみ出している。
  - 枠の内側は434×324 だが、中身はデスクトップ306px とタスクバー24px で330px ある。
  - `overflow: hidden` の箱はスクロールバーを出さないだけで、スクロールはできる。
  - スタートボタンにフォーカスが移ると、ブラウザがボタンを見せるために `#screen` を縦に4px スクロールしていた。
  - `#screen` 直下の `#scanlines` と `#crt-fx`（ガラスの縁の影）は絶対配置で、中身と一緒に動く。
  - この動きが黒枠のずれに見えた。
- 対策: `#screen` と `#desktop` を `overflow: clip` にした。
  - clip の箱はスクロール位置を持たないので、フォーカスでずれない。
  - clip に未対応のブラウザ向けに、直前の `overflow: hidden` は残した。
  ```css
  overflow: hidden;
  overflow: clip;
  ```
- 確認: ヘッドレス Chrome で Tab を押し、`#monitor` 配下の全要素のスクロール位置を記録した。
  - 修正前は、スタートボタンで `#screen` の scrollTop が4になった。
  - 修正後は、タスクバーの全ボタン・通知・スタートメニューの中まで回して0のまま。
  - オフライン時の平面モニターでも同じ。
  - 角丸の切り抜きと、デスクトップの位置は変わっていない。
  - ユーザーの実機でも問題なしと確認をもらった。
- 学習ポイント
  - `overflow: hidden` は見た目を切るだけで、スクロール位置を持つ。
    - フォーカス移動・`scrollIntoView`・ページ内リンクで動く。
    - スクロールさせたくない箱は `overflow: clip` にする。
  - clip はブロック整形文脈を作らない。
    - この2つの箱には浮動要素も上マージンのある子もないので、影響はない。
- 検証の道具: `.hl/pc3d/perf/cdp.py` にキー入力の操作 `["key", "Tab"]` を足した（`Input.dispatchKeyEvent`）。
  - 手順は `s_tab2.json`（3D）と `s_tab3.json`（平面モニター）。
- 作業ブランチ `fix/screen-focus-scroll` でコミットして push し、main へ fast-forward でマージした。

#### レイマーチングから three.js のポリゴン描画へ作り替え
- 経緯: 「three.js を使わない方が良いのか」と聞かれ、重さの原因は three.js の有無ではなく描き方（1画素ごとに距離関数を数百回）だと答えた。替える価値がある条件として挙げた「移動中のぼやけ・止まってから仕上がるまでの数秒が気になる」「物を足したい・動く物を置きたい」の2つに当たると言われた。
- 方式はユーザーが選んだ: three.js を CDN から読み込む（候補は、同梱して HTTP サーバー前提にする案と、自前のポリゴン描画）。README の「外部ライブラリなし」は書き換えた。
- 9月30日の処理落ち改善（レイマーチングのままの版）はコミットせずに捨てた。`.hl/pc3d/raymarch-pc3d.js` に退避してある。
- 構成
  - `index.html`: import map で `three` と `three/addons/` を jsDelivr の0.186.1に固定し、`integrity` に4ファイル（three.module.js・three.core.js・RectAreaLightUniformsLib.js・RectAreaLightTexturesLib.js）の sha384 を書いた。`js/pc3d-scene.js` を `js/pc3d.js` の前に読む。
  - `js/pc3d.js`: 元のカメラ・DOM の射影・入力・イントロ・埃・画面の色の見積もりはそのまま。描画は `import('three')` で読み込んだあと `window.PC3DScene` に任せる。`compileAsync` で全シェーダをそろえてから始める。読み込みに15秒かかったら平面モニターに戻る。
  - `js/pc3d-scene.js`: 形は角丸の断面を順につなぐ自前の関数で組んだ（筐体・テーパーした背面・ベゼルの面取り・キーボードの凹み・キー、マウスは角丸箱を球で切った形に頂点を押し下げる）。マグ・ランプは回転体、ケーブルは2次ベジェのチューブ、ブラインドはインスタンス描画。前面はフロッピーの凹みとグリルを穴にした平面（`ShapeUtils.triangulateShape`）。
  - 光: ランプは影つきスポットライト、月は影つき平行光源、ブラウン管は RectAreaLight（色は毎フレーム画面の平均色）、半球光源、ランプの照り返しの点光源。影マップは何も動かないので最初の1回だけ描く（`shadowMap.autoUpdate = false`）。
  - 質感: 元のシェーダの式を `onBeforeCompile` で MeshStandardMaterial に差し込んだ（壁の漆喰、机の木目、樹脂の色ムラと細かい凹凸、ランプの内側の発光）。月明かりは平行光源の色に元の `moonMask`（窓・ブラインド・桟の式）を掛けて、縞と柔らかい縁を元どおりに出した。
  - 後処理: 半精度の描画先に描き、霧（ランプの光芒は解析式、月明かりの筋は12点）を縦横半分の解像度で計算、明るい部分の抽出とぼかし、最後に元と同じ露出・周辺減光・ACES・ガンマ・粒子ノイズ。
  - 動いている間に遅れたフレームが20件中6件を超えたら、そのセッションの画素密度を0.8倍に下げる（下限は CSS 画素1つに1画素）。
- 結果（ヘッドレス Chrome、M1 Pro、GPU の完了を `readPixels` で待つ計測）
  - 1フレーム: 1440×900 は DPR1で4.3ms・DPR2で7.0ms、1728×1117 は DPR1で4.2ms・DPR2で9.2ms。
  - 往復テスト（窓4つを開いてヨー・ピッチ・斜め）: 両サイズとも DPR2のまま20ms 超が0件。
  - 起動: キャッシュなしで約0.5秒で準備完了。jsDelivr に繋がらないと約0.5秒で平面モニターに戻る。
  - 操作: ドラッグ・ホイール・クリックで戻る・テーマ切り替えを通し、着席時の DOM は `translate(500px, 172px)`・440×330。例外は以前からある `js/tetris.js:482` だけ。
  - 見た目: 構図・月明かりの縞・木目・キーの刻印は元と同じ。ランプの光が机とマグと PC の左側面に当たるようになった（元はシェードの距離関数の誤差で直射光がほぼ消えていた）。奥の壁のポスターが見えるようになった。
- 学習ポイント
  - three.js は r160 以降 ES モジュールしか配布していない。`file://` のページはローカルのモジュールを読み込めないが、通常のスクリプトから `import()` で CDN の URL を読むのは通る（jsDelivr が `Access-Control-Allow-Origin: *` を返す）。import map も効く。
  - `onBeforeCompile` に渡るシェーダは `#include` が未展開。ライトのループの中を書き換えるには `#include <lights_fragment_begin>` を `THREE.ShaderChunk.lights_fragment_begin` の置換結果に差し替える。
    ```js
    var lights = THREE.ShaderChunk.lights_fragment_begin.replace(
      'getDirectionalLightInfo( directionalLight, directLight );',
      'getDirectionalLightInfo( directionalLight, directLight );\n\t\tdirectLight.color *= pcMoonMask( vPcWorld );');
    fs = fs.replace('#include <lights_fragment_begin>', lights);
    ```
  - JS の数値を GLSL に埋め込むと `30` が整数になり、`float` との演算でコンパイルが通らない。`toFixed()` で小数にして埋める。
  - 半精度の4倍 MSAA は DPR2・1440×900 で約250MB になる。DPR1.5以上では MSAA を使わない。
  - 霧を全解像度で計算すると1728×1117・DPR2で4.2ms かかり、一番重かった。半分の解像度に落として約3ms 減った。
  - 原因の切り分けには、ライトを1つずつ点ける画と `MeshNormalMaterial` を `scene.overrideMaterial` にした画が効いた。`_pc3d.view().debug` から触れる。
- ユーザーの実機で動作を確認してもらい、作業ブランチ `feat/pc3d-threejs` に2コミット（f32d90e 描画の作り替え、ef5884b README）で push し、main へ fast-forward でマージして push した。
- 検証の道具: `.hl/pc3d/perf/cdp.py` は `CDP_ARGS` で Chrome の引数を足せるようにした（`--host-resolver-rules=MAP cdn.jsdelivr.net 127.0.0.1:9` でオフラインを再現）。`gpuprobe.js` が同期計測、`inter.js` が操作の通し確認。

### 2026-09-30
#### 視点移動時の処理落ちを改善
- 要望: 視点を変えるとときどき処理落ちする。特に PC を中心に左右へ回したとき。
- 計測（ヘッドレス Chrome、M1 Pro、1440×900・DPR2。GPU の完了を `readPixels` で待って測った）
  - 移動中の低解像度（792×495）が1フレーム12.8ms、全解像度の高品質1サンプル（2880×1800）が160ms。角度による差はほぼなかった。
  - 内訳は、影のレイ（ランプと月の2本）が約6.5ms、ケーブルのベジェ曲線・キーボード・AO がそれぞれ約2ms。
  - ウィンドウを4つ開いてヨー・ピッチ・斜めに往復させると、33ms 以上のフレームが3〜4割。止まって高品質パスが始まった直後に動かし直すと133ms の引っかかりが出た。
  - Chrome のトレースでは DOM スクリーンの再ラスタライズは1フレーム約0.25ms で、ヨーでもピッチでも `will-change` の有無でも変わらなかった。原因ではないので `will-change` は入れていない。
- 原因
  - 旧来の解像度調整は「6フレームの平均が18ms 未満なら上げる」ので、フレームを落とし始める所まで解像度を上げ続け、落ちては下げるを繰り返していた。
  - 止まるとすぐ全解像度パスを4帯（1帯40ms）で出していた。左右に回すと可動域の端（±0.85rad）でカメラが止まりやすく、そこで始まった帯の後ろで次の移動フレームが待たされる。左右で目立ったのはこれと考えている（実機では未確認）。
- 対策（シェーダ）
  - 包含箱での早期リターンを3つ追加した。机の上の物全体、キーの並び、ケーブル（制御点の箱＋半径と垂れ）。高品質パスの見た目は変わらない（前後のスクリーンショットで確認）。
    ```glsl
    // map(): 机の上の物はすべてこの箱に収まる
    if(sdBox(p-vec3(-0.078,0.22,-0.11),vec3(0.475,0.25,0.31))>res.x)return res;
    // mapSmall(): 旧来は p.y-0.006<res.x で、机の上ではほぼ常にベジェを2本評価していた
    if(sdBox(p-vec3(0.158,0.0045,-0.009),vec3(0.114,0.0045,0.075))<res.x){ ... }
    ```
  - 低解像度パスだけ、AO を5点から3点（抜いた点を台形則で重みに畳む）、影の刻みを0.0015〜0.06から0.0025〜0.09に広げた。レイの停止判定は画素の角度の半分（`uEps`）にした。高品質パスは従来の0.00015を上限に据え置いた。
  - 結果、低解像度パスは12.8ms から7.0ms、高品質1サンプルは160ms から96ms。
- 対策（JS のフレーム配分）
  - 移動中の解像度: `EXT_disjoint_timer_query_webgl2` で測った ns/画素から、表示間隔の55%に収まる解像度を求める。タイマーが無い環境では、直近10件の遅れ信号（rAF 間隔が表示間隔の1.6倍超、またはフェンスが3フレーム以上かかった）が3件以上で上限を0.8倍にし、遅れのないフレームごとに0.05%ずつ戻す。
  - 全解像度パス: 止まってから0.12秒（ドラッグ中は0.3秒）待って始める。帯は1つずつ、2フレーム以上前の仕事が GPU に残っていないときだけ出す。帯の行数は、高さを32区切りにして実測したコストから表示間隔の50%に収まる分を取る（上の壁は安く、下のキーボードは高い）。タイマーが無い環境は25万画素から始めて、遅い帯が出たら縮める。
  - 表示間隔は、重い描画が無いフレームの rAF 間隔の中央値で見積もる（120Hz なら予算も半分になる）。
  - 視点移動中は画面の平均色の取得（スタイルとレイアウトの強制計算を伴う）を止めた。軌道カメラの追従の打ち切りを2e-5から1e-4rad にした（約0.17px）。
- 結果（同じ往復テスト）: 1440×900 と1728×1117 のどちらでも、タイマーあり・なしとも20ms 超のフレームが0件（最大16.8ms）。移動中の解像度は0.52〜0.66倍。止まってから仕上がるまでは、変更前4.1〜5.9秒、変更後2.8〜5.0秒、タイマーなしだと6.1〜6.7秒。
- 学習ポイント
  - 前回の計測値は `gl.finish()` 相当で測っていて、GPU の完了を待っていなかった。Chrome の `finish` は GPU プロセスへの往復だけで、実際の GPU 時間は `readPixels` で同期するか、タイマークエリで取る。低解像度で約4倍の過小評価だった。
  - Chrome ではフェンスの `SYNC_STATUS` が GPU の完了から1フレーム遅れて届くことが多い。帯の約2割が「2フレーム後」に見え、2フレームを遅れと数えると帯が8行まで縮んで仕上がりに20秒かかった。遅れは3フレーム以上、次の帯を出す条件は「2フレーム以上前の仕事が残っていない」にした。
  - 予算を行ごとに減らすループを `while (left > 0)` で書いたら、浮動小数の丸めで残りが最小の非正規化数に張り付き、`n = left / perRow` が0になって抜けられずページが固まった。区切りごとに「収まるなら次の区切りへ、収まらなければ端数を足して抜ける」形にし、最大33回で必ず終わるようにした。
  - 影の刻みを16ステップに減らすと、ステップ切れのレイが光ったままになり、マグの周りと手前の机にランプの光が漏れた。24ステップに戻すと元の見た目に揃った。
  - ランプのシェードは `max(abs(cone)-0.0012, cq.y-0.048)` で底を切り取っているが、切り口の面で距離が約0.002しか返らない。影のレイは開口部を抜けるときに `k*h/t` で半影になり、机に届く直射光が数%まで落ちている。今の「光だまりが控えめな」見た目はこれが作っているので、性能改善では変えていない。
- 検証の道具: `.hl/pc3d/perf/`（gitignore 済み）に、pc3d を差し替えたページの生成（`make.py`・`sweep.py`・`shot.py`）と、標準ライブラリだけの Chrome DevTools Protocol クライアント `cdp.py`（任意のタイミングの撮影・JS 実行・トレース取得）を置いた。`--screenshot` と `--virtual-time-budget` はシェーダのコンパイル待ちで仮想時間を使い切ることがあり、`cdp.py` のほうが速く確実。

#### 3D の PC 本体を新規実装
- 要望: デスクトップを表示している PC 本体を3Dにしたい。古いモニター一体型、キーボードとマウスも置く、雰囲気重視、ブラウン管の質感。
- 途中で「three.js を使わないのか」と聞かれ、README の「外部ライブラリゼロ」「index.html を開くだけで動く」方針と、距離関数のレイマーチングの方が丸い樹脂筐体・柔らかい影を少ないコードで出せることを理由に自前 WebGL で続行した。three.js にするなら切り替えると伝えてある。
- 構成
  - `js/pc3d.js`: シーンのシェーダ（部屋・PC・キーボード・マウス・マグ・フロッピー・ランプ・窓とブラインド・ポスター）、合成とブルーム、カメラ、DOM の射影、埃と湯気の 2D オーバーレイ、入力。
  - `index.html`: `#pc3d-canvas`・`#pc3d-dust`・`#pc3d-hint` と、`#screen` 内に `#crt-fx`（ガラスの減光・映り込み・アパーチャーグリル・リフレッシュの帯）と `#crt-power`（点灯の輝線）を追加。`pc3d.js` は `boot.js` より前に読む。
  - `js/boot.js`: `window._pc3dPowerOn(cb)` があればブラウン管の点灯を待ってから BIOS 表示を始める。
  - `css/style.css`: `body.pc3d` 配下だけに効くルールを末尾に追加。WebGL2 が無い・シェーダが通らない・9秒以内にコンパイルが終わらないときは `pc3d` クラスを外し、従来の平面モニターに戻す。
- 描画の設計
  - 視点が動いている間は CSS px の0.33〜0.75倍の低解像度で1サンプル、止まったら全解像度で8（DPR2）〜14サンプルを帯に分けて積み上げ、終わったら重い描画を止める。~~M1 Pro の計測では高品質1サンプルが1440×900で18ms、2880×1800で62ms、移動中の低解像度が3〜5ms。~~ この値は GPU の完了を待たずに測っていた。`readPixels` で同期して測り直すと、高品質1サンプルが2880×1800で160ms、移動中の低解像度（792×495）が13ms（処理落ち改善前のコード、1440×900 は測り直していない）。
  - ブラウン管から部屋へ届く光（多角形光源の形状係数＋光沢面への映り込み）は別の描画先 `oScr` に分け、合成時に「画面の平均色」を掛ける。画面の平均色は壁紙キャンバスの平均と開いているウィンドウの面積から1秒ごとに見積もるので、テーマ切替でも再描画せず部屋の色が変わる。
  - 着席ビューはカメラの像面をブラウン管の面と平行にし（ピッチ0）、レンズシフトで下の机を入れる。これでスクリーンが常に440×330の長方形に投影され、DOM を整数座標へ置ける。構図は画面の高さに合わせて目の高さ（0.12〜0.24m）を選ぶ。
- 学習ポイント（ハマった点）

  - IQ の「改良版」ソフトシャドウ（`y=h*h/(2*ph)`）は前ステップの h だけ進む前提で、最小ステップ0.0015で底上げすると `y>h` になって半影が0（真っ暗）になる。右ベゼルに鋸歯状の影が出ていた原因。古典式 `res=min(res,k*h/t)` に戻した。
    ```glsl
    // before: float y=h*h/(2.0*ph); float d=sqrt(max(h*h-y*y,0.0)); res=min(res,k*d/max(0.0001,t-y));
    res=min(res,k*h/t); t+=clamp(h,0.0015,0.06);
    ```
